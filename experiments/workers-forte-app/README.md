# workers-forte-app

P1 for [#80](https://github.com/NamseEnt/fn0/issues/80): a real Forte app —
`forte build` output, unmodified — running on Cloudflare Workers through `jco`,
after `async: true` was dropped from the SDK's `wit_bindgen::generate!`.

Verified 2026-07-30 against a **Workers free plan** account.

## Result: it runs, and it does not fit the free plan

The whole app works: the guest returns `x-fn0-next: js` plus props, `server.js`
renders it, the SSR pass calls back into the guest over `/__self_invoke/`, and
the browser gets fully-rendered HTML with the hook cache serialized into it.
That holds under `wrangler dev` and on the deployed free-plan Worker.

What it does not do is fit **10 ms of CPU per request**. The deployed app returns
`1102 Worker exceeded CPU limit` on essentially every request; a page render costs
roughly 50-85 ms wall even warm on a laptop. See "The free plan enforces its
documented 10 ms" below — this is a limit finding, not a bug.

## Layout

| Path | What it is |
|---|---|
| `rs/`, `fe/` | `forte init --dev` scaffold plus one hook, so the SSR pass has a `/__self_invoke/` round trip to make. Nothing about it is Workers-aware. |
| `build.sh` | `forte build` → `jco transpile` → stage `worker/public/`. |
| `worker/index.js` | The `fetch` handler: assets, guest dispatch, the `x-fn0-next: js` handoff, and the in-isolate `/__self_invoke/` interception. |
| `worker/load-clock.js` | Imported before the heavy modules so its timestamp brackets their evaluation; ES imports are hoisted, so a `Date.now()` at the top of `index.js` would measure nothing. |
| `worker/gen/`, `worker/public/` | Generated by `build.sh`; not hand-edited. |

The host shim is `../workers-jspi-probe/worker/shim.js`, shared with the probe.

## Reproducing

```sh
./build.sh
npx -y wrangler@latest dev      # then curl localhost:8787
npx -y wrangler@latest deploy
```

`?stage=none|instantiate|wasm` short-circuits the handler at each step, which is
how the numbers below were taken.

## What had to change outside this directory

**`async: true` is gone from the three `wit_bindgen::generate!` sites**
(`forte/sdk/src/bindings.rs`, `forte/codegen/src/generate_routes/codegen.rs`,
`forte/sdk/src/test_harness.rs`). jco rejects what it produced; see the probe's
README. Dropping it makes every WIT `func` synchronous, so ~35 `.await`s went
away and `Instant::now`/`elapsed` and all of `forte_sdk::rand` became sync
functions — a breaking SDK API change, with `doc-db` and `fn0/control` as the
in-repo callers.

**`forte-react.ts` no longer hardcodes the loopback URL for SSR hook calls.** It
was building `http://localhost:${process.env.FORTE_PORT}/__self_invoke/...`,
which on Workers is `http://localhost:undefined` and throws `Invalid URL`. It now
prefers `globalThis.__FORTE_SELF_INVOKE_BASE__` and falls back to the port.

## Findings

### The SSR handoff inverts, and that is the easy part

On fn0 the host runs the wasm, sees `x-fn0-next: js`, and drives `server.js` in a
ski isolate. On Workers the JS *is* the entrypoint and the wasm is a module
inside it. `server.js` needs nothing for this: it is an IIFE that assigns
`globalThis.handler`, and importing it from the Worker is enough.

### `/__self_invoke/` should not leave the isolate

fn0 lets the SSR pass reach the guest over loopback HTTP. A Worker has no
loopback server, and pointing the SSR pass at its own public hostname would spend
a subrequest and a full network round trip per hook.

Instead the Worker sets `__FORTE_SELF_INVOKE_BASE__` to a sentinel origin and
patches `globalThis.fetch` to dispatch that origin straight into a component
instance. This holds no per-request state — cookies and body travel in the
request that `forte-react.ts` builds — so it stays correct when the isolate
interleaves requests.

Worth knowing before relying on that: `server.js` keeps the hook cache, the
collected cookies and the request cookie in *module* globals, so the SSR runtime
already assumes one request at a time per isolate. fn0 satisfies that with a ski
isolate per project. Workers does not guarantee it.

### Asset-first routing eats the request body

With Workers Static Assets the natural configuration is `run_worker_first: true`
plus an `env.ASSETS.fetch(request)` probe, falling through to the guest on 404.
Doing that unconditionally breaks every POST: the asset router reads the body, and
the guest then traps with `This ReadableStream is currently locked to a reader`
inside `Request::consume_body`. The probe has to be restricted to `GET`/`HEAD`.

### The free plan enforces its documented 10 ms

The probe's README recorded that the documented 10 ms free-plan CPU limit "is not
what is enforced", on the evidence that a ~1 s JS spin loop returned 200. **That
no longer reproduces.** Re-running the same `?burn=` endpoint on the same worker
and the same account, hours later:

| `?burn=` | ≈ CPU in node | Result |
|---|---|---|
| 1e6 | 1 ms | 200 200 200 |
| 5e6 | 5 ms | 200 200 503 |
| 1e7 | 10 ms | 503 503 503 |
| 1e9 | 960 ms | 503 503 503 503 503 |

The threshold now sits between 1e6 and 1e7 — the documented 10 ms. Treat the
probe's earlier reading as a measurement taken inside an anomalous window, not as
a standing property of the free plan.

Against that ceiling, three workers on one account, ten requests each:

| Worker | Bundle, gzipped | 200s |
|---|---|---|
| `jspi-check` — returns a JSON literal, no wasm | 0.2 KiB | 10/10 |
| `workers-jspi-probe` — one p3 component | 144 KiB | 3/10 |
| `workers-forte-app` — this app | 728 KiB | 0/10 |

A failing request is `1102`, and takes either ~0.5 s or ~6 s of wall time. The
signal is monotone in bundle size, and the failures survive spacing requests 25 s
apart, so this is per-request cost rather than a rate limit.

### Where the time goes

`wrangler dev`, warm isolate, arm64 laptop — an optimistic lower bound for what
the edge would charge:

| Stage | Wall |
|---|---|
| `?stage=none` — asset probe only | 3-6 ms |
| `?stage=instantiate` — plus a component instance | 4-19 ms (the instantiate call itself reports 1 ms) |
| `?stage=wasm` — plus the guest producing props | 17-30 ms |
| full page — plus SSR and the nested hook call | 48-86 ms |
| JS module evaluation at isolate start | 23 ms |

Deployed, the one request in a hundred that survives takes 0.7-0.9 s end to end.

Size is not the constraint the issue expected it to be: 728 KiB gzipped is well
inside the 3 MB free-plan limit, and `Worker Startup Time` is reported as 1-2 ms
at deploy. The 1.66 MiB core module compiles at deploy, not per request.

## Not covered

doc-db, vault, queue and object-storage all reach the platform by sending HTTP to
a placeholder host that the fn0 worker intercepts. On Workers there is no
interception layer outside the guest, so that is a trust-model decision rather
than a port, and it is independent of everything above. Same for the static page
cache, the presign and purge gates, and epoch-based CPU accounting.
