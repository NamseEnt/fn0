- This project uses English everywhere (code, comments, docs, commit messages).
- Do not modify `spec.md` without explicit user authorization.
- Comments: write only what code and history tools cannot carry. Run every comment through 3 filters, drop it if it fails any:
  1. Can it be expressed in code? (renaming, types, structure) → fix the code, not add a comment.
  2. Does Git (commit/blame) or the issue tracker already record it? → leave it there. No `// fixed issue #1425`, no change logs, no commented-out code.
  3. Would a competent teammate actually break something without this `why`? → if no, skip it even if it is a real `why`.
  - Worth keeping (passes all 3): non-obvious intent/rationale, unidiomatic code that looks wrong but is correct, workarounds / perf trade-offs / system limits, links to external sources or standards, `// TODO`, math derivations.
  - Never write: code restating (`i += 1; // add one`), syntax explanation, comments excusing bad names, commented-out code, history/bugfix notes, stale comments. Update comments when the code changes.
  - `why` is necessary but not sufficient — skip a `why` that is self-evident, has no consequence, is already encoded elsewhere, or is speculative/future.
- Names: a name states what the thing holds or does, and — when the code branches on it — which kind it is. A name that only states a category (`page`, `data`, `info`, `config`, `manager`, `handler`) fails: `private-object-storage` says what it holds and who may read it, `page` says neither. Where a distinction drives behaviour, put the distinction in the name: a bucket that GC may empty and a bucket that holds irreplaceable user data must not read alike. Spell names out — no abbreviations or acronyms (`ssr`, `cfg`, `req_id`) outside a single function body. If a comment is needed to explain what a name means, the name is wrong: rename and delete the comment.
- Names that escape the codebase — R2 bucket names, hostnames, env var keys, doc/table field names, published crate items — cannot be renamed cheaply once they exist. Settle them before the first write, and state the convention in the module that mints them.
- Rust `//!` doc comments are a separate category — they are public API documentation for `cargo doc` readers, not inline code commentary, so the "write only necessary comments" rule does not gate them. Add a `//!` at the top of `lib.rs`/`main.rs` (crate purpose, setup, gotchas) and at the top of a module file when its role/interactions are not obvious from structure; first line is a one-line summary. Do not add trivial `//! User module`-style headers to self-evident internal modules.
- Rust: verify with `cargo clippy`, not `cargo check`. 0 warnings + 0 errors.
- Rust file layout: `mod` declarations go at the very top of the file, then `use` statements below them. Do not put blank lines between consecutive `mod` declarations, nor between consecutive `use` statements.
- Telemetry is self-hosted on one node behind a single Cloudflare Tunnel: metrics in VictoriaMetrics (`metricsHostname`, basic auth built into the binary), logs and traces in loggytracy (`telemetryHostname`), Grafana for reading (`telemetryViewerHostname`). Judge health by probing the data plane, never a dashboard. loggytracy has no TLS and no authentication of its own — a Cloudflare Access service token authenticates callers at the edge and a Transform Rule overwrites `X-Scope-OrgID` there, so any change that exposes its listener another way, or that lets a caller's own tenant header survive, is a security change and not a routing one.
- `cargo publish` workflow on a local machine that holds publish credentials: do not wait for the `publish.yml` CI workflow at all. The flow is **bump versions → commit → `cargo publish` locally**, in that order (cargo publish refuses a dirty working tree, and commit-then-publish keeps the published crate's `Cargo.toml` consistent with git history). For a chain (e.g. `fn0-ski` → `fn0` → `fn0-worker`), publish in dependency order; crates.io indexing is fast enough that the next publish usually resolves immediately, and `cargo publish` waits for availability itself. CI publish and local publish are both idempotent — `already uploaded/exists` is a no-op — so a local push that also triggers CI is fine. When a deploy step needs a dependency crate published (e.g. `deploy-fn0-worker.sh` needs `fn0` before `fn0-worker`), publish it locally instead of blocking on CI.
- Internal tools deploy: `bootstrap-fn0-control.sh` runs only once after initial infra setup; `forte deploy` redeploys control; `scripts/deploy-fn0-worker.sh` redeploys worker.
- Build environment: development assumes an arm64 host. Dockerfiles are written for arm64 only — no cross-compile branches (`ARG TARGETARCH`, `--platform=$BUILDPLATFORM`, cross toolchains). Container-image Rust binaries are NOT compiled inside `docker build`: `scripts/build-rust-linux-arm64-bin.sh` compiles them via `docker run rust:bookworm` with the repo bind-mounted and `target`/cargo-registry on persistent named volumes, and the runtime Dockerfile only `COPY`s the resulting binary into a slim image. Reason: `docker build`'s `COPY . .` re-stamps source mtimes so cargo recompiles the whole dependency graph every time (measured: a one-line change rebuilds ~500 crates, ~10 min); the bind-mount + persistent volume keeps cargo incremental (same change rebuilds only the touched crate, ~1 min). Do not "simplify" this back to a `COPY`-into-`docker build` flow.
