## What these runs were, and what came of them

Two load runs over two object-store tiers: Tier B, an in-process
latency-and-fault store over `file://`, and Tier C, the real S3 protocol over
local MinIO. Both were reported as **FAIL**, and both failed on the same
behavioural gate rather than on a numeric one: the flush loop stopped making
progress, the WAL backlog grew, and part count froze.

**That is the result worth keeping.** The harness surfaced a real, pre-existing
engine bug that the local test suite could not see, which was the stated M7
objective. Everything numeric alongside it was noise, and the document said so
at the bottom while presenting it as evidence at the top.

Tier C did confirm one thing that is not a number and is not affected by the
harness's defects: **manifest CAS works over the real S3 protocol.** With
`OBJECT_STORE_CONDITIONAL_PUT=etag`, `PutMode::Create` and `PutMode::Update`
(If-None-Match / If-Match) succeeded, parts were published, the manifest
generation advanced, and no `Precondition`/`AlreadyExists` errors appeared. That
question is now answered at startup against the actual deployment target by
`ObjectStorage::verify_conditional_put`, which is strictly better than answering
it against MinIO — see [`LOAD_VALIDATION.md`](LOAD_VALIDATION.md).

## Citations in this document that were wrong

**`docs/m7_tier_c_result.json` does not exist and is not in the history.** This
document cited it as checked-in raw harness output for Tier C. It was not. Every
Tier C figure was therefore unverifiable from the moment it was written, and the
Tier C assets were later deleted along with the tier.

**The Tier B artifact disagrees with the document that cites it.** This document
recorded Tier B as **FAIL** at build `782e7ff`. The checked-in
`docs/m7_tier_b_result.json` records `"build_revision": "d2f2c4f"` and
`"verdict": "PASS"`, with flush progressing and the WAL backlog bounded. It is a
different build and the opposite verdict: a later run that someone left in place
without updating the prose beside it. Neither one describes the other.

**Decision: the artifact is kept, with a `_retired` header inside it explaining
what it is.** It is deliberately not deleted. It is the only checked-in evidence
of the harness's own defects — an offered rate the harness never came close to
reaching, percentile blocks over 167 and 8 samples, and a peak RSS of a few
megabytes passed against a 4 GiB gate — and [`VISION.md`](VISION.md) cites it as
exactly that. Deleting it would remove the evidence for the retirement while
leaving the retirement in place. It is not evidence about the engine and must
not be read as such. Note that `scripts/run_load_local.sh` overwrites this path
by default, so a future run will replace the file and its header together, which
is the correct outcome: a regenerated artifact is not a retired one.

## Struck

- **Ack, query, metric and tempo latency percentiles for both tiers.** Single
  connection, uncorrected coordinated omission, and eight-sample percentiles.
- **Peak RSS for both tiers.** Both figures were the load generator's own
  resident set: `current_rss_bytes` read `std::process::id()`, which inside the
  harness is the harness. They were a few megabytes of request buffers compared
  against a 4 GiB cap they could never have approached, and they were reported
  as "far under the cap" as though that meant something. The full correction is
  in [`LOAD_RESULTS.md`](LOAD_RESULTS.md) §3, and the principle it produced is
  the one that matters here: **a gate that cannot measure must not pass.** The
  rewritten harness reads `VmHWM` from `/proc/<server pid>/status` and fails the
  run when it cannot. `src/bin/m5_load.rs` had the original bug and is deleted.
- **Achieved event rate.** It is bounded by the harness's own structure, not by
  the engine.
- **The per-tier numeric target tables.** Both tiers "passed every numeric
  target" while failing the behavioural one, which in hindsight describes the
  targets rather than the engine.

Kept as behaviour, without magnitudes: eviction was observed on both tiers,
retention reclaimed parts on Tier B, restore probes ran with zero restore
errors, injected write errors were recovered with no acknowledged ingest loss,
and both tiers failed the flush-liveness gate.

## Configurations, for the record

Tier B: `file://` inner store wrapped by `LatencyFaultStore` (`LATENCY_MS=5`,
`LATENCY_JITTER_MS=10`, `READ_LATENCY_MS=20`, `ERROR_RATE=0.03`,
`FAULT_SEED=20260724`); `CACHE_MAX_BYTES=8 MiB`, `CACHE_EVICTION_INTERVAL=3s`,
`FLUSH_MAX_INTERVAL=2s`, `MERGE_INTERVAL=8s`, `RETENTION_PERIOD=20s`,
`RETENTION_GRACE_PERIOD=5s`. Workload: 45 s with a 10 s warmup, 100 events per
push, ~1 KiB events, one label set.

Tier C: MinIO via `docker compose`, server pointed at
`s3://signy/signy` with `OBJECT_STORE_ENDPOINT=http://127.0.0.1:9000`,
`OBJECT_STORE_ALLOW_HTTP=true`,
`OBJECT_STORE_VIRTUAL_HOSTED_STYLE_REQUEST=false`,
`OBJECT_STORE_CONDITIONAL_PUT=etag`. No fault injection. Workload: 25 s with a
5 s warmup.

Machine: `Darwin arm64` (Apple Silicon), 8 logical CPUs, 16 GiB — a developer
laptop, not the 4-vCPU / 16-GiB reference machine. The fault seed was
`20260724` and the workload seed reported by the harness was `1592598566`.
Configuration and seeds are recorded because the *shape* of a run is worth
reproducing even when its output is not worth citing.

## Identified bottleneck (the blocker) — the finding that survives

**WAL compaction wedged the flush loop after the first successful compaction,
losing flush liveness under any sustained object-store-backed run.**

Root cause: `compact_wal` (`src/journal/compaction.rs`) writes a durable
compaction-state file at phase 2 to make the rename/fsync boundary idempotent,
but that file was **never removed after a successful compaction** during live
operation — only `replay.rs` cleared it, and only for phase 1, on startup. After
a compaction the WAL is truncated and the checkpoint resets to 0, so subsequent
checkpoint offsets live in a **new coordinate space**. The next compaction's
offset is smaller than the stale phase-2 offset recorded in the *old* coordinate
space, so `compact_wal` hit the `offset < state.offset` guard and returned
`"WAL compaction checkpoint moved backwards"`. The flush loop then retried the
same doomed checkpoint every second forever: part count froze, the WAL grew
unbounded, and the memtable never drained.

The evidence for it does not depend on any measurement being accurate, which is
why it stands:

- Reproduced with the Tier B fault store **and** with Tier C MinIO under **zero**
  fault injection — neither backend-specific nor fault-induced.
- A separate no-fault `file://` control run reproduced it as well, after only a
  couple of successful flushes.
- It affected only object-store-backed runs, because `advance_checkpoint`
  compacts (`journal.compact_checkpoint`) only when `remote_cache.is_some()`;
  local-only runs use `set_checkpoint` and were unaffected — which is why the
  existing local test suite never caught it.

The fix landed as its own change: clear the compaction-state file once a
compaction is durably complete, and treat a surviving phase-2 state on startup
as already-done and remove it, so the next compaction starts in a clean
coordinate space instead of comparing against a stale absolute offset. Already
wedged instances recover through an upgrade.

## The caveats were the real result

These were recorded at the bottom of the original document, correctly, and then
ignored in favour of the tables above them. They are now the headline.

- **The flat ack latency was a client artifact, not a server signal.** The
  harness uses a single synchronous connection and the journal batches appends
  up to `max_batch_ms`, so each lone in-flight push waited out the batch timer.
  Every ack percentile in the document was therefore a measurement of the
  harness's concurrency, and the diagnosis was written down beside the numbers
  it invalidated.
- **The achieved rate was far below the offered rate**, bounded by that same
  single connection plus the batch wait rather than by server backpressure. This
  is coordinated omission in its plainest form: the harness stopped issuing when
  the server slowed and never recorded the delay it owed. The figures are quoted
  in [`VISION.md`](VISION.md), where they are framed as evidence about the
  harness rather than about the engine.
- **The numeric verdict was deferred to hardware that is now out of scope.**
  "Validated on target-class hardware later" was how numbers from a machine that
  could not validate them were published in the meantime. There is no later
  target-class run coming; there is a harness rewrite.
