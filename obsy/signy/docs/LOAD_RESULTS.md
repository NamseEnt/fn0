# Load and measurement results (retired)

> **Retired 2026-07-29. No number in this document may be cited until it has
> been regenerated by the rewritten harness.**
>
> Every measurement here was produced by `src/bin/load.rs`, which cannot measure
> what it claimed to. It is single-connection with one request in flight and
> `Connection: close` per request. Its pacer keeps a nominal schedule but the
> stopwatch starts at the actual send, so every percentile is the latency of a
> request the harness had already waited for permission to make. Its corpus is
> one hardcoded label set over `"x".repeat(...)` padding — cardinality 1,
> near-zero entropy. Its queries fire inline on the push thread, so reads never
> contend with writes. Some of its percentiles are over eight samples, where a
> p95 is the maximum. And until the correction in §3 its RSS gauge read the load
> generator's own process. [`VISION.md`](VISION.md) "The ruler comes before the
> work" states the case in full; rebuilding the ruler is M8 in
> [`todo.md`](../todo.md).
>
> The tables are struck. What survives is what never depended on the magnitudes:
> what each run was asking, the hypotheses that were tested and refuted, the
> harness defects the runs exposed, and the counts that are properties of this
> code rather than of a run. Each section says what remains unknown, which is
> now most of it.

The policy these runs were made under is in [`LOAD_VALIDATION.md`](LOAD_VALIDATION.md).
One line of it survives intact and is the reason anything here is still citable:
**keep reproducible facts in tests, not in prose.** Every finding below that is
still good is still good because a test pins it.

All runs: `Darwin arm64` (Apple Silicon), 8 logical CPUs, 16 GiB — not the
target specification of 4 vCPU / 16 GiB, and for most of §10 not even idle.

## 1. Removing group-commit latency (P1-3)

**Asked:** whether ack latency was set by the journal's batch timer or by the
storage backend. The batch loop consumed `max_batch_ms` even when the channel
was empty.

**Survives:** the diagnosis, which never rested on the absolute values. With
`file://` or MinIO, with or without injected latency, every pre-fix value
clustered at the same place. A latency indifferent to the backend is a timer,
not I/O. The loop no longer waits out a timer on an empty channel, and
`journal::tests::sequential_appends_do_not_wait_out_a_batch_timer` pins the
behaviour: 20 sequential appends must finish within 1.5 seconds, where the old
default took 4.

**Unknown:** what ack latency this engine has. One request in flight is the
condition that maximizes a group-commit timer's cost and erases its benefit, so
the run measured the pathological case and nothing else was ever run.

## 2. Tenant-fragmentation cost (N3)

**Asked:** what tenant count alone costs in part size, with everything else held
fixed.

**Survives, and it is structural:** row groups stop at tenant boundaries, so
**tenant count is a lower bound on row-group count**. Parquet carries column
metadata per row group and this engine carries a bloom per row group, so the
fixed cost is emitted per **(tenant, part) pair** — the pair is the unit, not
the row. The amplification follows from that alone:

```
amplification ≈ 1 + (fixed cost per pair) / (compressed bytes per row × rows per tenant in a part)
```

The consequences of the formula are the finding. The ratio is not a function of
tenant count; it is a function of **rows per tenant per part**, so it is large
exactly when the denominator is small — which is also when the absolute amount
is small. Because `merge_target_part_rows` is one million, a high ratio is
transient: it holds from flush until merge picks the part up. The only wall
merge cannot cross is daily partitioning, so the variable that sets steady state
is *rows per tenant per day*. And a tenant's pair count is set by **how many
parts contain that tenant's writes** — a function of other tenants' ingest
volume, not its own. `signy_part_tenant_segments` is that count.

The affected resource is resident memory and startup, not storage: eviction
removes `data.parquet` while `PartReader::open_internal` retains the sidecar for
as long as the part exists.

**Struck, and why:** the byte figures came from
`part::tests::tenant_breadth_sets_the_row_group_floor_and_what_that_costs`
rather than from the harness, so they are deterministic and reprintable on
demand. They are struck anyway, because the line they were computed on is the
harness's padded, near-zero-entropy synthetic. This section already recorded
that repeating the measurement with realistic logs carrying a `trace_id` and a
latency gave a far smaller ratio, because such lines compress far less well —
and the harness was not changed afterwards. A ratio whose denominator is set by
the compressibility of a fake corpus is a property of the corpus. The R2 cost
estimate that followed from it is struck with it.

**The second fixed location cited here was wrong.**
`merge::tests::layout_gauges_count_tenant_part_pairs_not_rows` does not exist
and no function by that name has ever existed in this tree. The tests that do
exist are `merge::tests::layout_totals_count_tenant_part_pairs_and_survive_a_silent_merge`
and `merge::tests::merging_parts_removes_their_pairs_from_the_totals`, cited
correctly at the end of §6.

**The fixed per-pair cost has grown since, and the increment is struck too.**
`TenantSegment` now carries the tenant's byte range in `data.parquet` and a
CRC32 of exactly that range, so the `meta.json` segment gained two fields per
(tenant, part) pair. The byte figure for that increment came from the same
synthetic corpus as everything else in this section, so it is struck with them;
the shape is not struck, and it is worth naming plainly: it is a fixed cost paid
on every part written, for a read path §6's own measurement decided against.
Fixed location: `part::tests::each_tenant_segment_records_the_byte_range_of_its_own_row_groups`,
which checks the recorded range against the Parquet footer that actually decides
the layout, against its own checksum, and against its neighbours.

## 3. Backpressure holds at the limit

**Asked:** what the engine does when ingest greatly exceeds flush capacity. The
memtable limit was lowered to 8 MiB and events were pushed without pacing, over
500 tenants, with S3-like latency injection and a small injected error rate.

**Survives:** the system did not buffer without bound. It reached the limit and
**rejected**, the memtable ended just under its configured limit, the WAL
backlog stayed bounded, and the server's `ingest_errors_total` did not move. A
very large number of 429 responses is not a failure — it is backpressure
working. That accepted requests stayed fast while unacceptable ones were refused
immediately is the shape that matters, and it is the shape that is now pinned by
tests rather than by a run: `ingest::tests::push_is_refused_once_the_memtable_is_over_its_limit`
and `ingest::tests::push_is_refused_once_the_wal_backlog_is_over_its_limit`.
Both test **engaging and clearing**. Latched backpressure would remove an
instance from service permanently after one burst, which is worse than unbounded
growth.

**Unknown:** every latency figure from this run, for the reasons in the header,
and peak RSS, for the reason immediately below.

### Correction to this run

**The peak RSS recorded here was the load generator's, not the server's.**
`current_rss_bytes` read `std::process::id()`, which inside the harness is the
harness. So the figure was a few megabytes of request buffers, it was compared
against a 4 GiB gate it could never have exceeded, and it was written down as an
engine result. The tell was in the table itself: a peak of a few megabytes next
to an 8 MiB memtable in the same run. **A gate that cannot measure must not
pass** — and it must not silently pass either, which the intermediate fix still
allowed by reporting `null`.

The rewritten harness reads `VmHWM` from `/proc/<server pid>/status`, so the
peak is the kernel's own high-water mark rather than whatever a poll happened
to catch, and a run that could not read it **fails**. `src/bin/m5_load.rs` had
the same bug and has been deleted, so every m5-era memory number in this
repository is the harness's own RSS and there is no longer a binary that can
produce another one.

### Harness defect revealed by this run

The first run numerically failed with an error rate of 0.995. **The harness was
counting 429 as errors.** A run that was defended exactly as designed was
reported as a 99.5% error rate — the thing being counted as catastrophe was the
feature preventing catastrophe. 429 was separated into `push_throttled` and
excluded from the error rate (after `e925334`). This is the first of several
places where the verdict was a property of the harness rather than of the
engine.

## 4. Relationship between flushes and part count

**Asked:** whether flushes map one-to-one to parts, after an earlier run
observed far fewer parts than flushes and that looked like an engine bug.

**Survives:** the cause of the anomaly. `scripts/run_load_local.sh`
unconditionally overwrote the caller's `MERGE_INTERVAL`, so a run believed to
have merge disabled was merging every eight seconds. Merge was doing its job.
The script was fixed (around `ea6b0b3`). The lesson is that the configuration a
run believes it has is worth verifying against the configuration the server
reports.

**Invalidated:** the follow-up run that produced a one-to-one result was
configured with `MERGE_INTERVAL=3600s`, which §8 later showed does not disable
merge at all. This run had a merge in it. What it establishes is therefore
weaker than what it claimed.

## 5. Eviction → restore

**Asked:** whether an evicted part is restored from the object store and read.
This is not observable under the default configuration, and that is normal
behaviour rather than a defect: merge consolidates recent parts and its output
is always local, and retention deletes old data so the probe queries an empty
range. Three settings have to be changed together to make the round trip
happen at all:

```
MERGE_INTERVAL=3600s  RETENTION_PERIOD=off  CACHE_MAX_BYTES=524288
LOAD_RESTORE_LOOKBACK_SECONDS=40
```

**Survives:** restore was observed with zero restore errors under that
configuration, and the requirement that the configuration be built deliberately
for the question.

**The limitation this run recorded, since fixed:** the probe could not
distinguish "restored and read" from "nothing matched", because both return 200.
The probe now counts the rows that came back (`restore_probe_rows`,
`restore_probes_with_rows`), so the distinction no longer has to be inferred
from a server-side counter.

**Unknown:** restore latency. Those percentiles were over a handful of samples.

## 6. The layout axis (N3)

**Asked:** whether resident sidecar cost or fragmentation is the binding memory
constraint, using two runs differing only in whether merge runs.

**Survives:** **merge is the lever on pair count.** Pair count tracks part
count, and merge is what bounds part count. The gauges added for this question
agreed with what the unit test prints for a synthetic part, which is the useful
part of the result: the model behind §2 describes a real workload and not only a
fixture.

**Also survives, and it reversed the working assumption:** at this scale the
sidecars are a rounding error against what merge transiently holds, so the
binding memory constraint is merge, not fragmentation. The gauges were added to
test the opposite belief.

**Invalidated:** the merge-off column. `MERGE_INTERVAL=3600s` does not disable
merge (§8), so both "merge off" runs contained a merge. Every ratio in this
section is between a run with many merges and a run with one, not between merge
and no merge.

**Struck:** every RSS figure, every pair count, and the extrapolation to the
10,000-part configuration built on them — §8 later showed that extrapolation
assumed a part shape the configuration in question does not produce.

### Following the FAIL: two hypotheses, both wrong, one bug

The merge-on run ended `FAIL` while merge-off passed. Two explanations were
proposed and both were tested rather than assumed. They are kept here rather
than quietly replaced.

**"Peak RSS is the merge budget" — wrong.** Cutting `merge_max_memory_bytes`
eightfold moved peak RSS by less than the spread between runs and changed no
verdict. The run with no injected errors peaked *highest* of the four and
passed. Peak RSS tracked whether merge ran at all, not what merge was allowed to
materialize. §7 takes this further and refutes the successor hypothesis too.

**"The FAIL is memory pressure from merge" — wrong.** The highest-RSS run of the
four is the one that passed.

**The next explanation offered was also wrong.** It was that health recovery
degrades as reporters multiply: `mark_remote_healthy_since(epoch)` restored
health only by CAS from the epoch the caller observed before its operation, so a
failure by any other worker in between defeated that worker's recovery.
Sampling `remote_healthy` every 250 ms through both runs refutes it — the run
with **fewer** reporters had the **worse** duty cycle. Both flapped. The
PASS/FAIL split between them was the terminal sample landing on different sides
of a signal that changed every few seconds: luck, not a behavioural difference.

**What it actually was:** a single failed request meant "the store is down", and
`/ready` reads that. At a write-error rate the engine survives with no ingest
errors and no lost data, readiness flipped more than ten times a minute. An
orchestrator watching that pulls an instance in and out of service over an error
rate that cost nothing.

Health is now hysteretic: three consecutive failures with no success between
them mark the store down, and one success clears it. Re-measured on the same
workload, both runs read healthy nearly all the time with a handful of
transitions instead of dozens.

**And the harness gated on the terminal sample**, which is what made its verdict
a coin flip. It now samples through the run and gates on the fraction.

### What survived the fix, and what it turned out to be

The merge-on run ended with a much larger WAL backlog than the merge-off run.
Sampling it every 500 ms over a ten-minute run answers whether that grows: it
**oscillates**, with a slight downward trend and a second-half mean below the
first-half mean. Merge and flush do contend, and flush catches up. **Bounded,
not growing.** N8 is a tuning note, not a defect.

The peak during that run was several times the terminal sample, so the
single-sample reading was luck as well — the third time in this section that
gating on a terminal sample produced a number that meant nothing. That is the
one lesson from §6 that generalizes past its own numbers.

The harness now samples the backlog and asks the question that distinguishes the
two cases: **does flush ever catch up.** A backlog that rises and falls is flush
keeping up in bursts; one that only rises is flush losing. Comparing halves
would have worked here and failed a short run, which is all ramp and no plateau;
drainage holds for both. The ceiling it is judged against is the engine's own
`max_wal_backlog_bytes`, because reaching that engages backpressure, and
engaging is the design working — the old fixed harness target failed runs whose
backlog was oscillating exactly as intended.

Fixed locations: `merge::tests::layout_totals_count_tenant_part_pairs_and_survive_a_silent_merge`,
`merge::tests::merging_parts_removes_their_pairs_from_the_totals`.

## 7. Where the memory actually goes (N9)

**Asked:** why peak RSS was several times higher with merge on, when cutting the
merge memory budget eightfold barely moved it. §6 left allocator high-water
retention as the recorded hypothesis.

**Refuted.** Watching RSS every 500 ms through a run and for 90 seconds after it
shows RSS returning to its starting value, and merge continuing to advance
through the idle tail while RSS sat at idle. It is neither retention nor a leak.

**What it is:** live memory held while ingest, flush and merge run at once,
released promptly by the allocator. The budget knob did not move it because the
groups being merged were far smaller than the budget — with parts of a few
megabytes, `merge_max_input_bytes` was never the binding constraint, so lowering
it changed which merges were split rather than how much any of them held. A knob
that is not binding does not become binding by being turned.

**The operational consequence is a sizing rule, not a defect:** peak RSS is very
much larger than idle RSS, it is reached within about a minute of load starting,
and it returns to idle when load stops. An instance sized from a quiet
screenshot is sized far too small. **The multiple is struck** — the run that
produced it had cardinality 1, no concurrent readers and an achieved rate far
below its offered rate, so the peak is the peak of a workload nobody runs. The
direction of the advice survives; the magnitude does not. [`RUNBOOK.md`](RUNBOOK.md)
and [`CONFIGURATION.md`](CONFIGURATION.md) are marked accordingly.

Incidentally this is the only evidence on the long-running-leak axis: memory
returned fully to its starting value after sustained load. It is not a
substitute for a soak, which looks for drift over hours, but a leak large enough
to matter over hours would probably have been visible here.

## 8. Startup at 10,000 parts (P1-11)

**Asked:** how startup time scales with part count. Merge was suppressed and
small flushes accumulated until the registry held about ten thousand parts, then
a clean stop and a restart timed from process start to `/ready`.

**Survives, and it is the most reusable finding in the document: the cost is
checksums, not round trips.** Every part's bloom, stream index and metadata are
read from local disk and verified, and that happened three times — the catalog
restore at the start of `reconcile_local_cache`, the one at its end, and again
when the registry opened each part. The object store was barely touched.

One of the three was redundant. The final restore exists to fetch catalog files
for parts the reconcile itself published, and a clean restart publishes nothing,
so it re-validated ten thousand catalogs for no result. It is now skipped when
the manifest did not change. The remaining two passes are real work, and
reducing them needs the manifest format change P1-11 describes.

**Also survives: the extrapolation in §6 was wrong, and this run says why.**
Resident sidecar cost at ten thousand parts came out far below what §6 projected,
because these parts are tiny — about ten tenants per part against §6's roughly
ninety. The §6 extrapolation assumed a part shape this configuration does not
produce. Extrapolating a per-pair cost across a different part shape is
extrapolating across the variable that sets it.

**Also learned, and it invalidates other sections: there is no way to switch
merge off.** `tokio::time::interval` fires its first tick immediately, so
`MERGE_INTERVAL=99999s` still merges once at startup. Accumulating this part set
worked only because the load outran that single tick, and a later tick during
the measurement consolidated the whole set into a handful of parts in under two
minutes — correct behaviour, but it means **every "merge disabled" run in this
document had one merge in it.** §4's one-to-one flush-to-part result and §6's
merge-off column are both weaker than they were written to be, and both are
marked above.

**Struck:** the total startup time, the per-phase breakdown, and the resident
and query figures quoted alongside them. The ranking of the phases — catalog
restore dominating, journal recovery instant after a clean stop — is the part
that survives, and the shape of the fix did not depend on the seconds.

## 9. Object-store operation counts

The cost unit of this whole design. Per-tenant objects were rejected on
Cloudflare R2 Class A cost, and nothing since had checked that arithmetic
against what the engine actually issues.

**This section survives better than any other, because counts are not
measurements of a machine.** Amounts cannot be measured locally — a local
backend has no price — but the number of requests per operation is a property of
this code, so it is the same here as against R2. It is now pinned by
`object_storage::tests::publishing_a_part_costs_a_fixed_number_of_requests`
rather than quoted from a run.

**A flush costs four PUTs and one GET.** Three PUTs are the part's immutable
files (`data.parquet`, `index.bin`, `meta.json`), the fourth is the manifest,
and the GET is the manifest it read to replace. The run recorded here measured
*five*, because the bloom and the stream index were separate objects then; they
have since been consolidated into one `index.bin`. The earlier edition of this
section left the five-PUT tables in place and told the reader to "divide the PUT
column by 5 and multiply by 4". That was wrong to publish: a table nobody can
read without performing arithmetic on it will be read without performing the
arithmetic. The tables are struck, and the recomputed version — arithmetic on
four, not on five — lives in [`CONFIGURATION.md`](CONFIGURATION.md) where the
setting it prices is documented.

**Publication cost does not grow with the manifest.** Publishing the tenth part
into a nine-part manifest costs exactly what publishing the first into an empty
one costs. That property matters more than the constant, and it is what the test
asserts.

**Retirement costs four DELETEs per part**, one per immutable file, unbatched.
R2 does not charge for deletes, so this costs nothing there; on a backend that
bills them, `DeleteObjects` would collapse them to one request per batch. That
is a change worth making only against a backend that bills for it. Deletes come
from `garbage_collect_orphans`, which runs only after retention has retired a
whole part and only past `retention_grace_period` — one hour by default, which
is why a short run sees no DELETE and no LIST traffic at all. The orphan sweep
is two LISTs, one per immutable prefix, plus the two manifest GETs it compares
them against, and it runs only on a retention pass that actually retired
something.

**What this says about the bill, structurally:** R2 bills Class A per request,
deletes are free there, and GETs are Class B and an order of magnitude cheaper.
So the number that matters is PUTs, and PUTs are a function of the flush
interval and nothing else — a flush skips an empty memtable, so an idle instance
costs nothing, while an instance with continuous traffic flushes on every tick.
The flush interval is also the RPO, so it is a deployment trade between cost and
durability rather than a number this repository should pick for anyone. What was
missing was the price of the choice, and it is now readable at
`signy_object_store_operations_total`.

**Struck:** the run's measured operation table and the R2 dollar figures derived
from it. The counts are recomputed and priced in [`CONFIGURATION.md`](CONFIGURATION.md);
the prices there are quoted from R2's published rates and will change, while the
counts will not.

## 10. Tier D: two hours, 500 tenants, a restart and a fence

The duration run: about two hours, 500 tenants, `file://` with fault injection,
sampled every 15 seconds.

**Read no latency, throughput or memory number from this run.** The machine was
compiling and running the test suite for most of it, so response times and peak
RSS describe CPU starvation. That was recorded honestly at the time and it is
now the general case rather than the exception: the whole document was produced
on a developer laptop with no control over what else was running. The
behavioural gates below do not depend on the machine being idle, which is
exactly why they are the gates.

### Behavioural gates — these survive, as booleans

| gate | result |
|---|---|
| Zero loss of acked data | **pass** — `wal_replayed_records` and `wal_replayed_entries` were both 0 after the restart. A clean shutdown left nothing to replay, so nothing was duplicated either |
| WAL backlog bounded | **pass** — it oscillated and its second-half mean did not exceed its first-half mean |
| RSS stable, no upward trend | **pass** — first-half and second-half means equal, no trend. The absolute value is meaningless under build contention |
| Flush, merge and retention all progress | **pass** — all three advanced throughout; the flush errors were the injected rate and all recovered |
| Zero ingest errors | **pass** — across every request in the run |
| Graceful shutdown lossless | **pass** — force-flush complete on the first attempt |
| Fencing | **pass** — a second instance on the same prefix made the first log `fenced by a newer writer` and exit 1 |
| Data readable after restart | **pass** — all 500 tenants' streams returned rows over the expected window |

**`remote_healthy` read true in every sample taken across the two hours**,
against a sustained injected write-error rate. Before the hysteresis fix (§6)
the same signal flipped more than ten times a minute and read false for a large
fraction of a run. This is that fix holding over hours rather than over a
minute, and it is a duty cycle rather than a terminal sample, which is the whole
point.

### Restart

Restart to `/ready` was fast, at two parts. There is nothing to compare it
against in §8 — that measurement was at ten thousand parts, and §8's finding is
that startup is linear in part count. What this confirms is the other end of the
line: with merge working normally, part count stays small and so does startup.
The seconds are struck; the shape is the finding.

### What the soak found

**Graceful shutdown took about two minutes and nearly all of it was
avoidable.** The flush loop stopped a second after SIGTERM and force-flush took
milliseconds — and then the merge task ran on, completing two more merge groups
that it *started after the signal*. The merge loop selected on the drain only
between ticks, and a tick holds up to `merge_max_groups_per_tick` groups.

Fixed: the tick now checks the drain before taking each group. The group already
running still finishes, because abandoning it throws away the work and leaves
its inputs to be merged again on the next boot. Nothing new starts.

Nothing shorter could have found this. The earlier runs never accumulated enough
parts for one tick to hold more than a single group — which is an argument for
duration runs surviving the harness rewrite, not for trusting this one's
numbers.

## 11. Query-heavy: the memory budget's largest term, exercised once

**Asked:** what the read side of the memory budget actually costs. Every run
above is ingest-dominated — `src/bin/load.rs` issued its queries from inside the
push loop, one per `query_every` pushes, so query concurrency was one by
construction, and `max_concurrent_query_scans × max_query_memory_bytes`, **four
of the five gigabytes** `peak_materialized_bytes` reports at startup, had never
been touched by a load run. Independent reader threads and a query-heavy profile
were added to drive it: 24 readers, 24 tenants, 120-second scan windows at
`limit=5000`, a 256 KiB cache so the readers miss, retention at 600 s, 2000 eps
offered, 150 s with a 45 s warmup, Tier B faults on.

**The tables are struck with the rest of this document.** This ran on
`src/bin/load.rs`, and the retirement applies to its numbers as much as to §1–§10:
it achieved a third of its offered rate, because 24 reader threads and the push
loop shared the client's 8 cores. What follows is what never depended on a
magnitude.

**Survives — the scheduler can be filled, and the server can prove it was.**
`signy_query_scans_in_flight_peak` and `query_scans_queued` are high-water
marks the server keeps rather than gauges the harness samples, because a burst
that fills the scheduler and drains between two scrapes is invisible to sampling.
A run that did not fill the scheduler has not measured the term it was launched
to measure, so the harness refuses to call it a pass. That refusal is a property
of the harness and survives its rewrite.

**Survives — small queries queue behind large ones.** The scan scheduler admits
by arrival order and knows nothing about cost, so a dashboard refresh waits
behind up to `max_concurrent_query_scans` wide scans. This is head-of-line
blocking rather than saturation: nothing is overloaded, and the queue is doing
exactly what it was written to do. It is read off the admission path, not
inferred from this run's percentiles, which is why it outlives them. **It is also
the shape of the answer P3's "tune resource limits to operational targets" was
waiting for, and it says the knob to turn is not a memory cap** — separating
interactive scans from bulk ones shortens the queue without spending budget.
Recorded as a finding, not acted on — and **superseded before either knob was
turned, see §12**: making the expensive query cheaper moved the same probe back
inside its target without touching the scheduler at all.

**Survives — a concurrency defect nothing serial could find.** The first run
failed most of its restores with fault injection *disabled*, on `File exists
(os error 17)` and `failed to cache part … data.parquet: No such file or
directory (os error 2)`. Restores hold a *shared* lifecycle guard on purpose, so
object-store latency does not block writers exclusively; several readers missing
the same evicted part therefore all enter `download_part` at once, and they
staged into a directory named for the part alone, `remove_dir_all`-ing it on the
way in — each tearing down what the others had downloaded. The losers were
counted as object-store failures, and each called `record_remote_failure`, which
is what drives `/ready` to 503. This is the same class of mistake the publish
path documents and guards against for `INPUTS_CHANGED_ERROR` — "never as a store
failure, reporting it as one takes `/ready` to 503 over a benign race" — left
unguarded on the restore path, in both the log and the trace domain. Serially it
is unreachable, which is why nine load runs never saw it. Fixed by staging each
attempt under its own directory, and **pinned by
`concurrent_restores_of_one_part_all_succeed`**, which fails 11 of 12 restores
against the old scheme — a test, so it is citable where the run that found it is
not.

**Unknown, and left open by that fix:** two restores can still collide replacing
the same part directory, one deleting it between the other's remove and rename.
Renaming the three files individually into a directory that is never deleted
would close it — parts are immutable, so concurrent restores write identical
bytes and per-file renames cannot produce a wrong combination. Not done here: it
changes a commit path, and it belongs with the format change that range GET
needs.

Raw output: [`query_heavy_result.json`](query_heavy_result.json), kept for the
counters the server produced rather than for the rates the harness reported.

## 12. Folding metric rows instead of collecting them

**Asked:** why a `rate()` over a busy stream came back refused rather than
answered.

**What it was:** `MetricEvaluator` never wanted the rows. Its first act was to
reduce them to a `(timestamp, value)` per label set and drop every line, so the
`Vec<(SharedLabels, LogEntry)>` the scan handed it existed only to be discarded
one step later — and `max_metric_rows` bounded that intermediate. The ceiling was
on something the client was never going to receive.

**The fix is code, not a measurement, and survives on its own.** The scan takes a
sink. The log paths get the one that collects rows, sorts and groups them, which
is what they did before; the metric path gets one that folds each row into
per-series samples as it arrives, keeping sixteen bytes an event and none of the
text. Both go through the same scan rather than beside it, because that is where
the deletion mask lives and a second scan would be a second place to forget it.
**Pinned by `a_metric_query_folds_rows_a_log_query_could_not_materialize`**,
which answers a metric query over half a megabyte of lines under a 64 KiB budget
and shows the same rows still refused as a log query — a test, so it is citable
where the run that motivated it is not.

`SIGNY_MAX_METRIC_ROWS` is removed. What a metric query costs is still
bounded, by things that bound something real: `max_query_scan_bytes` for the read
— enforced per part rather than checked afterwards — `max_query_runtime` for the
wall clock, and `max_metric_series` / `max_metric_samples` for the answer.

**The tables are struck, as in §11.** The re-run used the same retired harness on
the same shared-core client, so its ratios carry the caveat its absolute numbers
do.

**Survives — the ordering it settled.** Making the expensive query cheaper moved
the dashboard probe back inside its target *without touching the scheduler*, so
§11's "the knob to turn is not a memory cap" resolves one step further: at this
workload it was not the scheduler either. Head-of-line blocking is still the
shape of the tail — the p99 barely moved — but it stopped being the binding
problem. That is a statement about which change to make first, and it does not
depend on the magnitudes that showed it.

**Unknown:** everything the ratios claim. Whether the fold is worth the
evaluation-count multiple it reported, and what peak RSS does at a workload that
is not sharing eight cores with its own load generator, are for the rewritten
harness to answer.

## What is not measured at all

- **Anything the rewritten harness has not produced yet.** That is every number
  formerly in this document.
- **Long-running leaks.** §7 is suggestive and is not a soak.
- **Concurrent read/write behaviour, by a harness that can measure it.** Every
  run before §11 issued queries inline on the push thread, so reads never
  contended with writes. §11 did contend them and found a real defect doing it,
  but on the retired harness and on a client whose cores its readers and its push
  loop had to share, so it settles the direction and none of the magnitudes. What
  the suite pins is narrower and does survive:
  `concurrent_restores_of_one_part_all_succeed`.
- **Any workload with realistic cardinality or entropy.** Every run used one
  label set and padded lines.
- **Anything against Loki.** The claim in [`VISION.md`](VISION.md) has never been
  measured against anything.
