## Fixed workload and budgets

- Both backends use a common 256 MiB cgroup maximum and 192 MiB high boundary across setup, measurement, and both full-population oracle epochs, with zero backend swap. The driver and uncharged ARC/host memory remain outside that budget.
- E2 seeds 2,048 rows per tenant: 1 MiB of 512-byte value payload. E3 seeds 32,768 rows per tenant: 16 MiB of value payload. Keys have 16-byte PK and 16-byte SK; all seed rows share a PK. Values are deterministic pseudorandom bytes. Actual representation is larger than payload.
- The all-active condition has registered=active and no opened-idle tenants. Each active tenant has one absolute-deadline arrival lane at 50 API calls/s, queue bound eight, and a shared maximum of eight in-flight requests. Requests time out after five seconds; drain is bounded at fifteen seconds. Seed is 20261027.
- The mixed profile is Get/Query/write=40/20/40. Query always reads the first sixteen seeded rows. Get walks a deterministic full-period modular seed-row sequence. Mutations overwrite/delete/reinsert a separate fixed sixteen-key lane, rather than uniformly rewriting the seed dataset. Half the writes are conditional; widths are 1/4/16 with an 80/15/5 mix; ten percent of mutations are deletes. Preserve these harness semantics and report this limited write working set.
- B-link explicitly uses segmented coalesced bases, background checkpoints, 256 KiB WAL segments, and a 1 MiB checkpoint threshold. A1 stays disabled. These are experimental settings, not defaults.
- Shared RocksDB uses one 64 MiB cache and one 32 MiB WBM, 1 MiB per-tenant write buffers, one global flush thread, one global compaction thread, and 64 open files per tenant. WBM writer stalls remain disabled; native sharing and options must be verified. These are a bounded reference, not maximum-tuned RocksDB.
- Main periodic kernel/native sampling is 100 ms. Preserve explicit gaps, truncation, native observation byte bounds, and the separately sampled process RSS/CPU scope.

## Service objective

Define an experimental objective, not a production requirement. Every active tenant must schedule its complete offered count, admit and successfully finish every request, have no conflicts/errors/timeouts/drops, complete at least 99% by offer end, and meet scheduled-arrival-to-completion per-operation p99 bounds: Get < 2^23 ns (8.388608 ms), Query < 2^24 ns (16.777216 ms), Write < 2^26 ns (67.108864 ms). At least 100 observations per operation per tenant are required. These boundaries match the existing power-of-two histogram exactly; do not report interpolated exact percentiles or silently substitute the original provisional 5/10/50 ms product thresholds.

Both complete-population oracles, accounting, PID/start-time identities, worker membership before runtime/backend construction, actual shared options, synchronous durability, shutdown, and untruncated observations remain required. High events are allowed and reported; a worker OOM, resource rejection, or operational timeout is a failed operational-capacity outcome, even if measurement never begins. Keep setup/open/oracle failures distinct from offered-load failures. Corruption, mismatched provenance, invalid accounting, or unexplained errors stop the investigation instead of becoming performance results.

Capacity is the largest tested count satisfying the full objective, accompanied by the next tested failure or an explicit upper censor. Operational memory capacity and SLO capacity are separate. A successful larger cell does not establish monotonicity at untested counts. An OOM without workload counters is not a measured zero-throughput workload. Reduced observations from overloaded cells need not match admitted-work fingerprints; compare deterministic recipes and report realized divergence.

## Bounded adaptive sequence

1. Screen paired E2 counts 1, 4, 8, 16, and 32, and paired E3 counts 1, 2, 4, and 8, for thirty seconds each. Alternate which backend runs first. Stop increasing an individual backend after its first operational resource failure; continue its paired reference only within the frozen grid. Stop before any unsafe projected disk expansion. If both fail the SLO, further safe cells only describe the operational/resource frontier, not an SLO winner.
2. If a stage has both a passing and failing SLO screen, refine at most two integer midpoints between the largest pass and smallest larger failure. Do not change dataset, rate, objective, budget, or sampling after seeing results. A largest count that passes is an upper-censored screening result.
3. Select the paired largest common SLO pass and smallest tested count above it at which either backend fails. Run three fresh paired sixty-second repetitions at each selected count, rotating backend order. If no common pass exists, repeat the one-tenant condition three times and report the lack of a common demonstrated capacity. If a memory failure occurs before measurement, preserve it and do not repeatedly provoke identical OOMs merely to obtain a median.
4. Compare 100 ms with 1,000 ms sampling at the largest common passing E2 count using one additional sixty-second pair at 1,000 ms. Compare this sensitivity against the three main repetitions, including CPU usage and p99 bucket ranges. This is a bounded perturbation observation, not proof of zero instrumentation overhead. Main results retain 100 ms sampling regardless of this outcome.
5. Run a separate sparse E3 pair with registered equal to the highest safely completed common grid count, one active and one opened-idle tenant if the population permits, for sixty seconds. If no such population has at least three tenants, explicitly omit this sensitivity. Setup and oracle still open the entire population and must fit the same budget. Do not fold sparse results into all-active capacity.
6. Run one paired 180-second mixed-write maintenance observation at the largest common confirmed E2 count, or one tenant if none is confirmed. Retain synchronized tenant arrival/checkpoint demand and observe WAL/checkpoint progress, native flush/compaction properties, memory/disk samples, and first/last intervals. It must include multiple checkpoint cycles to support even a short maintenance observation. Staggered demand, growing-key churn, long reads, crash recovery under pressure, and production steady-state remain future work.

Screening durations, confirmation durations, sparse conditions, and sampling sensitivity are separate cohorts. Do not combine them to invent repetitions. A 180-second hot-overwrite cell cannot prove indefinite stability or aggregate cold-disk behavior.
