# Three-engine durable workload harness

This harness compares `main-btree`, `planned-blink`, and RocksDB 11.8.1 through one request generator and one OS-thread-per-client driver. DODB's Tokio runtime and coordinator are engine internals; they do not change the external client count or request supply model. The planned B-link setup disables parallel execution and borrowed-page views, uses one coordinator worker, a 64 MiB page cache, a 256-entry queue, and groups up to 64 currently queued requests without a collection delay. Main B-tree uses the same queue and group request limit with a 4 MiB group byte limit. RocksDB uses a 64 MiB block cache, WAL enabled, synchronous writes, one `WriteBatch` per logical transaction, and pipelined writes disabled.

The shared core request set has a 10,000-row uniform seed, 16-byte keys, 512-byte values, and Query16 requests distributed across seeded partitions and exclusive cursors. Full query keys, order, row count, and values are checked. Point Get checks all value bytes; DODB also checks the seed commit revision recorded from each successful seed transaction, separately from read results. Mixed reads use a bounded sample history. DODB reads are checked against commit revisions and successful transaction history. RocksDB has no adapter-visible per-value revision, so its sampled read value must match the full seed value or the exact full value of an observed successful mutation for that key; this proves value lineage but makes no freshness or revision claim. Missing bounded history, partial histories, or overflow is inconclusive and fails run acceptance.

`build-native.sh BUILD_ROOT ROCKSDB_SOURCE` builds RocksDB and both harness binaries on the current machine architecture. It requires a clean DODB checkout, a clean fresh RocksDB checkout at commit `abeebd9630f11bd08c28b7bd43c7bdfc62050654`, and the exact `v11.8.1` tag. Build outputs stay in `BUILD_ROOT`; no source checkout is used for result output.

`run-matrix.sh smoke|core|sustained|scale|scale-sustained OUTPUT_ROOT [fresh|resume]` requires a new output root for a fresh run. By default, the output root must be on `dodbbench/db` ZFS mounted at `/bench/zfs/db`. Debian runs can set `CROSSDB_DATA_ROOT` to a fresh directory on the existing filesystem and set `CROSSDB_REQUIRED_FSTYPE=any` and `CROSSDB_REQUIRED_SOURCE=any`. The runner uses the configured data root for both result and database files. It runs engines serially, creates a new database directory for every execution, records failed attempts, validates each JSONL record, and writes environment snapshots and checksums. Resume skips only executions already accepted by the validator. Smoke covers Get c16, distributed Query16 c16, and mixed 50/50 c16 width 1; its throughput is not part of the core or sustained results.

The core suite contains 12 conditions, three repetitions, and three engines for 108 executions. Every engine and repetition for a condition uses the same seed; each condition has its own seed. The sustained suite contains mixed 50/50 width 1 and mixed 95/5 width 8 at c16, three repetitions and three engines for 18 executions using the same seed within each condition. The scale suite accepts `CROSSDB_SCALE_CLIENT_COUNTS` as comma-separated counts and measures mixed 50/50 and pure writes at each count; DODB Tokio runtime workers follow the requested client count and are recorded in the run. The scale-sustained suite accepts `CROSSDB_SCALE_REPRESENTATIVE_CLIENTS` and checks the two mixed profiles at that count for 120 seconds. All use 10,000 rows, 16-byte keys, 512-byte values, a 2-second warmup and a 10-second measurement for core/scale, and a 10-second warmup and 120-second measurement for sustained runs. Sustained output includes 10-second throughput, separate read/write latency, RSS, WAL and engine metric windows.
