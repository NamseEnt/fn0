Reports are checked for the actual executor, backend, allocator/lock mode, caller or admission slots, and health coverage. Raw reports explicitly state that conditional locking is not applicable. The plans were generated with `--prepare-only`; journals store their selected counts and fingerprints.

The controller fixes source `ee6cd94f1a4e7b2bab7af603bc8983bbf8184542` and both release binary hashes, runs cases serially, and journals each completed case so a completed case is never repeated. It starts each child in its own process group. Every second it records process-group RSS and `/proc/meminfo`, `/proc/vmstat`, and `/proc/diskstats`; every five seconds it records database file size. At 3 GiB process-group RSS, 1,500 MiB host `MemAvailable`, 4 GiB database size, or 180 seconds, it sends TERM to that group, checks group membership through the grace period, then sends KILL to any remaining members even if the `/usr/bin/time` parent has already exited. A disappearing group between check and signal is handled safely. Timeout, watchdog stop, or failed validation preserves the database and evidence and stops the matrix. An interrupted in-progress journal entry requires inspection before resuming. `/usr/bin/time -v` remains the final whole-process peak RSS check and includes validation/reopen.

The process-group self-check in `evidence-ee6/watchdog-process-group-selfcheck.py` was run locally and on the authorized OCI host. The grandchild ignores TERM, so the check verifies that the target parent may exit first, the remaining group is still found and killed after the grace period, and an unrelated sentinel group remains alive. Both outputs are preserved as `evidence-ee6/watchdog-process-group-selfcheck.json` and `evidence-ee6/watchdog-process-group-selfcheck-oci.json`.

Each case uses a 10-second warmup and 30-second measurement with 1-second engine-health sampling, `log1024`, stage and detailed diagnostics disabled, seed `20261013`, 10,000 rows, 512-byte values, width 16 enabled, 100,000,000 call cap, full-window enforcement, and a 5,000,000-entry service ledger cap. All service overwrite cases use 1,024 slots per client; the new-key cohort uses the same service parameters with the new-key generator; unconditional cases use 256 preseeded slots per client.

## Preliminary five-minute `rw20/c16` resource budget

Cohort A completed all 60 cases at source `ee6cd94f1a4e7b2bab7af603bc8983bbf8184542`. The seven-path preflight budget and physical-WAL recovery source path are in `FIVE-MINUTE-RESOURCE-BUDGET.md`; actual selected-run resource results are in `FIVE-MINUTE-RESULTS.md`. The preflight figures remain estimates and are distinguished from the measured five-minute values.

The source bounds overwrite mutation keys at 16,384 per client for the enabled width-16 profile. With 16 clients and 10,000 seeded rows, the validation state can reach up to 272,144 keys. The 30-second reports contain 142,910–143,627 Blink rows, 154,936–158,589 service rows, and 163,308–163,920 core rows, so longer execution can still grow the state toward this bound before it plateaus. At 512 bytes per value, the maximum value payload alone is about 139 MiB; key, map, revision, allocator, and scan-verification overhead are additional and are not included in that payload figure.

The run directories also show post-reopen sizes of 803–808 MiB for Blink, 116–167 MiB for the service path, and 163–170 MiB for core. These are observed 30-second footprints; neither these sizes nor the ledger are claimed to scale linearly. The 30-second measurement ledger is approximately one tenth of the selected five-minute window. A conservative linear count projection is 1.19–1.20 million entries for Blink, 1.43–1.51 million for service, and 1.61–1.64 million for core, plus the separate 10-second warmup ledger. This remains below the configured per-tenant 5,000,000-entry cap, while expected-state rows and engine disk/WAL/backlog must be watched as they grow.

The bounded histogram, 100-client-prefix fingerprints, caller count, and preseed input plan have fixed configured capacities. The replay ledger and its validation clones grow with successful transactions; the expected-state map, seen-key set, native database state, and WAL/SST backlog have separate costs. At 30 seconds, reported collector peaks were 26.3–38.1 MiB and whole-process maximum RSS was 421–719 MiB, including validation and reopen. The five-minute controller enforces its 3 GiB process-group RSS cap, 1,500 MiB runtime host-memory reserve, process-group TERM/KILL watchdog, one-second host and database-size sampling, 12 GiB per-case database cap, 900-second timeout, full-lifetime `/usr/bin/time -v` record, and per-case cleanup only after final/reopen validation and database-log manifest creation. The recovery five-minute preflight passed with 73,173,204,992 bytes free and 8,385,257,472 bytes MemAvailable.

The RocksDB paths recorded 29 health samples in a 30-second measurement with a 32-sample capacity and complete coverage. The sampler supports at most 1,024 entries, enough for a 300-second window at one-second intervals. Blink reports this engine observation as unsupported while retaining process and host samples. These readings are diagnostic; they do not prove sustained capacity or absence of writer starvation.
