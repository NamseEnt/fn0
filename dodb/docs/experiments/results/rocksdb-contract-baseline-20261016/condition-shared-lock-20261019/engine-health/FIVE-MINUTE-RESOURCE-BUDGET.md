# Five-Minute Resource Budget

This document records the preflight budget and actual resource results for the completed 21-case five-minute confirmation at source `ee6cd94f1a4e7b2bab7af603bc8983bbf8184542`. The selected scope is A `rw20/c16` on Blink, RocksDB service Shared-16, and synchronous core Shared-16, plus E unconditional `c64/width16` on raw, service Shared-32, synchronous core with 64 dedicated callers and no admission-slot limit, and Blink; each path has three repetitions. The service's 32-slot admission applies only to the service backend. It retains the frozen release binaries, 10-second warmup, 300-second measurement, 1-second engine-health interval, and diagnostics disabled. The requested process time is 6,510 seconds (108.5 minutes), before setup, validation, reopen, and cleanup. This selects 21 cases from the original 111-case plan; the other 90 definitions are outside this five-minute confirmation.

All A and E observations below are from the three completed 30-second runs. Those runs contain a 10-second warmup plus a 30-second measurement, so their 40-second disk observations are scaled by 7.75 only for the explicit disk budget proxy. This is not claimed as an exact long-run growth law. A forecasts use the largest observed whole-process `/usr/bin/time -v` RSS, the remaining overwrite row-domain at 4,096 bytes per row, nine times the measured 30-second measurement/merged/replay-clone capacity as a conservative 300-second collector increment, and a fixed 512 MiB validation/runtime reserve. E has a fixed preseeded 262,144-row domain; its RSS proxy adds 512 MiB to the largest observed whole-process RSS. Both estimates still require the 3 GiB process-group watchdog and 1,500 MiB runtime `MemAvailable` reserve.

The E report records `baseline_read_all_rows_retained_during_measurement=false`, drops final and reopened row vectors after their oracles, and uses fixed-size latency histograms. Its `/usr/bin/time -v` maximum covers the full child lifetime, including validation and reopen; the smaller sampled RSS fields cover only the measurement interval. The unconditional reports' explicit memory accounting does not include native engine memory or the expected-state structures, so the full-process measurement and watchdog remain the controlling checks.

The service's Blink production path is `dodb-server/src/lib.rs` `open_shard` → `BlinkStore::open_path` → `open_with_wal` → `open_internal`. `WalLog::open` at `dodb-storage/src/wal.rs` scans with `ScanMaterialization::Recovery`. For Blink, `keep_batches` is false in that mode; recovery replaces the latest image in a `BTreeMap<PageId, RecoveredWalPage>` and inserts only the first record for each page. The map is therefore bounded by distinct recovered pages rather than every historical batch, while the current pending batch and page map still use memory proportional to the recovery input/page domain. `open_internal` takes these recovery pages, applies them, drops the map, then loads the data file. The server's shutdown clears and shuts down open shards but does not checkpoint them. The logical-WAL transaction-vector path does not apply to this measured service path. These code facts are useful for the budget but do not remove the need to measure reopen RSS and WAL growth.

The five-minute controller enforces a 3 GiB process-group cap, a 1,500 MiB runtime host-memory reserve, a 12 GiB per-case database cap, and a 900-second child timeout. Its fresh preflight requires at least 26 GiB free on the measurement filesystem (12 GiB case allowance + 4 GiB retained evidence + 10 GiB reserve) and at least 4,794,089,472 bytes `MemAvailable`; the recovery run passed with 73,173,204,992 free bytes and 8,385,257,472 bytes `MemAvailable`. It preserves one-second host/RSS/database samples, 300-second health coverage, whole-child `/usr/bin/time -v`, logs and manifests; any failed database is retained. Successful cases are removed only after validation, reopen, and file-hash manifest checks. ## Observed five-minute resource results

The run reports and retained `/usr/bin/time -v`, host, and live-budget samples supersede the projections above for the selected cases. Across all 21, the lowest sampled `MemAvailable` was 3.14 GiB against the 1,500 MiB runtime reserve; the largest whole-child RSS was 1,505.4 MiB against the 3 GiB process-group cap; and the largest live sampled database was 8.29 GiB against the 12 GiB cap. All cases completed within those runtime limits. The report's measurement-window process RSS and whole-child RSS differ because the latter includes setup, validation, reopen, and teardown. Neither measurement separates harness allocations from native RocksDB allocations.

The selected case reports measured RocksDB `block-cache-usage` up to 32 MiB and `cur-size-all-mem-tables` up to 72.5 MiB. These are property observations, not the effective configured block-cache capacity. A's estimated simultaneous collector capacities range from 190.2 to 216.1 MiB, while E lists fixed histogram/revision collector capacities totaling 57.9 MiB. The logical live value data is 132.02–132.07 MiB for A and 128 MiB for E, excluding keys and engine metadata. These figures do not provide a harness/native RSS split or prove a cache-to-resident-dataset ratio. Full path-by-path results and accounting limits are in [FIVE-MINUTE-RESULTS.md](FIVE-MINUTE-RESULTS.md).
