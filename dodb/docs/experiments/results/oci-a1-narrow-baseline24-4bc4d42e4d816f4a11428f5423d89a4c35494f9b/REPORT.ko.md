# OCI 좁은 기준 측정 24회 결과

## 범위와 조건

이 보고서는 이번 요청에서 새로 고정한 좁은 조건표의 결과다. 확인되지 않은 과거 공식 24회 조합표와 동일하다고 표현하지 않는다. 결과는 이 조건에서의 계측·정확성 확인과 기준 비교이며 엔진 채택 결론이 아니다.

- OCI `opc@217.142.246.204`: Oracle Linux Server 9.8, ARM64 Neoverse-N1 2 CPU, RAM 10 GiB.
- `/bench/zfs/db`는 `dodbbench/db` ZFS 실제 마운트다. 실행 전후 111 GiB 여유, `recordsize=4K`, `sync=standard`, compression/atime off였다. DB/WAL, TMPDIR, 결과 파일은 ZFS 아래에 두었다. 루트 XFS는 489 MiB 여유, 99% 사용이었다. 실행 전후 phase0-bench/cargo 경쟁 프로세스는 없었다. 기존 데이터를 지우거나 인프라를 변경하지 않았다.
- 소스 SHA `4bc4d42e4d816f4a11428f5423d89a4c35494f9b`, checkout clean. `phase0-bench.rs` SHA-256 `bae7b7b6fe13223c6ef579715c773b87a843b1b8caeeff4659a67818d7387e90`, `Cargo.lock` SHA-256 `9702ecfb45d6edab98f5aa3e849ad6f456faed7f75d5b37bd9b545eb2d5d4da6`.
- Release ARM64 바이너리는 동일 SHA·source·Cargo.lock·Cargo config의 기존 검증본을 재사용했다. 바이너리 SHA-256 `9f8cadd3d432b95e9bb9ac4570da70e104fc5ad4254e39bbcb1953251a5a1981`. Rust/Cargo 1.97.1, native target `aarch64-linux`. `.cargo/config.toml`에서 ARM64 `-C target-feature=+crc` 설정이 적용되며 설정 파일 SHA-256 `d7f22f835a631b08459a9662e207df20f4abfbf8110e198cbac04582f5c42c9f`다. JSON `rustflags=unset`은 환경 변수 `RUSTFLAGS`가 비어 있음을 뜻하며 Cargo 설정 파일과 별도다. 기존 동일 SHA Release 테스트 기록은 42개 통과, 실패 0이다. 이번 실행은 소스를 편집하거나 다시 빌드하지 않았다.
- 공통 명령 인자: `--sync-mode real`, Tokio worker 2개, working_set 4096, key/value 16/64 bytes, cache_capacity 256, uniform, warmup 1초, 측정 목표 5초, 프로세스마다 `--repetitions 1`, Query `read_limit 16`, `--blink-collection-policy current`, `--blink-workers 2`, `--parallel-workers 0`, group limit 64, group bytes 4,194,304, queue 256, transaction mode unconditional. Get/Query는 reader 1개. Mixed는 writer 1개 + reader 1개, **총 2개 client 작업**, 50/50, 폭 4 또는 8이다.
- seed는 반복 1–3에 `0xd0db2026`, `0xd0db2027`, `0xd0db2028`. 엔진 쌍은 같은 seed·입력 설정을 썼다. 조건마다 반복 1 main→planned, 반복 2 planned→main, 반복 3 main→planned로 순차 실행했다.
- 목표 warmup+측정 합계 144초다. seeding·drain과 runner 준비는 별도였다. 각 실행의 명령, 상태 시각, 측정 duration과 종료 offset을 manifest·로그·원본 JSONL에 남겼다.

## 실행 유효성 및 재실행

초기 runner는 빈 `width` TSV 열을 Bash의 whitespace 구분자로 읽으면서 뒤 필드를 당겨 첫 12개 Get·Query 행의 command 변수를 비웠다. 실제로 `bash -c ""`가 호출되어 종료 코드 0을 남겼지만 phase0-bench는 시작하지 않았고 JSONL도 생성되지 않았다. 빈 로그와 이 상태는 보존했다. 해당 12개를 성공으로 세지 않았다.

폭이 지정된 mixed 12개는 실제로 실행되어 원본 JSONL을 보존했다. 파서 수정 뒤 Get 6개와 Query 6개는 고유한 attempt-02 명령·파일명으로 재실행했다. 첫 시도 파일을 덮어쓰지 않았다. 최종 유효 결과는 mixed attempt-01 12개와 Get/Query attempt-02 12개, 총 24개다. 모든 원본 JSONL의 `repetition=0`; 외부 반복 번호는 manifest에서 별도로 연결했다.

최종 24개 모두 source SHA·clean 상태·source/Cargo.lock/binary hash·실행 인자·Release/ARM64·requested duration·client aggregation 검사를 통과했다. 오류, overload, conflict, conflicted transaction은 모두 0이다. Get 검증 표본 존재와 상태 `passed`, Query 응답 전수 검사, mixed revision 검증 표본 및 history 누락 0을 확인했다. 모든 JSONL에서 클라이언트별 집계가 전체 합계와 일치한다.

`cpu_utilization_percent_machine` 중앙값은 Get/Query에서 두 엔진 모두 약 49.8–50.0%였다. Mixed 폭 4는 main 57.99%, planned 9.90%, 폭 8은 main 56.70%, planned 19.79%다. mixed 누적 WAL sync 시간은 약 4.16–4.44초/목표 5초이며 sync 건수도 기록됐다. 이는 sync 대기와 CPU 사용량을 함께 분해할 조사 후보이지 인과 결론은 아니다.

측정 요청은 5,000ms다. JSON의 실제 경과 duration은 5,000–5,004ms, 마지막 client 종료 offset은 약 5,000.000–5,001.955ms이며 drain을 포함한다. client 종료 편차는 Get/Query 0, mixed 최대 약 1.954ms다. 모든 실행의 detailed metric은 `per-run.tsv`와 원본 JSONL에 있다.

## 해석의 한계와 다음 조사

mixed 검증은 bounded revision history를 사용했다. 이번 이력 추정 사용량은 한도 이내이고 누락 0이지만, 장시간 측정에서의 한도 초과 가능성이 해결된 것은 아니다. Query16에서 planned의 처리량이 낮고 p95 지연이 높았으므로 실제 분산 범위의 Query 경로와 지연 구간 분해가 조사 후보이다. Mixed에서 관측한 WAL sync 누적 시간, CPU 사용률, 처리량을 함께 분해하면 durable sync 대기·queue 대기·엔진 실행 비용을 조사하는 데 도움이 된다. 현재 결과는 원인이나 성능 향상의 인과를 증명하지 않는다.

이 결과는 단일 reader Get/Query와 고정 2-client mixed 기준이다. 다중 client 확장성, 엔진 전체 채택, crash recovery 내구성을 입증하지 않는다. 계획된 120초 측정은 수행하지 않았다. 세 반복만으로 장기 변동을 추정할 수 없고, 특히 mixed 폭 8 planned는 throughput CV와 p99 반복 차이가 있어 추가 반복에서 재확인할 수 있다.

## 산출물

이 디렉터리에 원본 JSONL 24개, 최초 no-op을 포함한 모든 로그와 상태, 두 시도의 manifest·정확한 명령, host/build 기록, 검증 JSON, Query 입력 지문 비교, 실행별 TSV, 조건 요약, 한국어 보고서, OCI raw/log 체크섬 대조 파일이 있다. `SHA256SUMS`는 최종 artifact 전체의 체크섬이다. `remote-content-checksums.txt`는 OCI에서 계산한 실행 JSONL과 로그의 SHA-256이다.
