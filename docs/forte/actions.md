# Actions

Actions are server-side functions called directly from the frontend. They are similar to "server actions" or "RPC endpoints." Each action is a separate `.rs` file in `src/actions/`.

## Defining an Action

An action file must define three items:

```rust
// src/actions/create_post.rs

pub struct Input {
    pub title: String,
    pub body: String,
}

pub struct Output {
    pub post_id: u64,
}
// Output can also be an enum:
// pub enum Output { Ok { post_id: u64 }, Error { message: String } }

pub async fn handler(req: forte_sdk::ForteRequest<'_, Input>) -> Output {
    // req.body is the deserialized Input
    // req.jar gives access to cookies
    Output { post_id: 42 }
}
```

Requirements detected by code generation (`forte_codegen::has_action_handler`):
- A struct named `Input`
- A struct **or enum** named `Output`
- A `pub async fn handler`

## HTTP Contract

Actions are routed to `POST /__forte_action/{name}` where `{name}` is the file stem.

- **Request body**: JSON-encoded `Input` (deserialized via `forte_json::from_slice`)
- **Response body**: JSON-encoded `Output` (serialized via `forte_json::to_vec`)
- **Response headers**: `Content-Type: application/json`
- Cookies written to `req.jar` are sent back as `Set-Cookie` headers.

## Registration

`forte build` auto-generates `src/actions/mod.rs`:

```rust
// Auto-generated by forte build
pub mod create_post;
pub mod delete_post;
```

And wires them into the dispatch function in `route_generated.rs`. You do not need to register actions manually.

## JSON Encoding

Actions use `forte_json` for serialization:
- Rust `snake_case` fields → JSON `camelCase` keys
- JSON `camelCase` keys → Rust `snake_case` fields on deserialization
- `Option::None` fields are **omitted** from the JSON output (not serialized as `null`)
- Enum variants use `{"t": "VariantName"}` for unit variants and `{"t": "Name", "v": ...}` for data-carrying variants

See [json.md](./json.md) for full details.
